# Cloud-Based Real-Time Fraud Detection

This project implements a **cloud-inspired real-time data processing pipeline** for fraud detection, developed as part of a data engineering portfolio. The system is implemented locally using **Docker-based microservices** and demonstrates core real-time data engineering concepts rather than production-level complexity.

## System Overview
The architecture consists of three main components:
- **Apache Kafka** as a distributed message broker for real-time event ingestion
- **Apache Spark Structured Streaming** for stream processing and aggregation
- **Python-based Producer** to simulate transactional data streams

All components are deployed as isolated Docker containers and orchestrated using Docker Compose.

## How It Works
1. A Python producer generates transaction events and publishes them to a Kafka topic.
2. Kafka acts as a buffering and ingestion layer, decoupling producers and consumers.
3. Spark Structured Streaming consumes the Kafka stream, performs preprocessing, window-based aggregation, and applies simple rule-based fraud indicators.

## Data Source
The system processes **simulated streaming data** generated by the Kafka producer.  
For realism, the producer can optionally be seeded with a local dataset (e.g., the Kaggle Credit Card Fraud Detection dataset) to preserve basic statistical and temporal characteristics.  
The dataset itself is **not stored in this repository** due to size and is used only locally during simulation.

## Quick start

Requires Docker Compose and Python. Run from the repository root:

```bash
docker compose up -d zookeeper kafka
docker compose exec kafka kafka-topics --bootstrap-server kafka:29092 --create --if-not-exists --topic transactions --partitions 3 --replication-factor 1
docker compose up -d spark
python -m pip install -r producer/requirements.txt
python producer/producer.py --num-records 1000 --rate 50
```

Start the producer after Spark is running because the stream reads new Kafka offsets. Inspect `docker compose logs -f spark` and the generated `output/` directory; stop services with `docker compose down`. The producer generates synthetic transactions when no optional seed CSV is supplied.

## Reproducibility & Maintainability
- The entire infrastructure is defined as **Infrastructure as Code (IaC)** using Docker Compose.
- The system can be reproduced on any machine with Docker installed.
- The microservice-based design supports scalability and independent component evolution.

## Reliability and Governance
- Local Docker Compose setup uses one Kafka broker; the quick-start topic has three partitions and replication factor 1. This is an educational setup, not a fault-tolerant cluster.
- Simulated transactions use synthetic numeric user identifiers; no real customer records are included.
- The performance figures below describe a local test run, not a production service-level guarantee.

## Performance Tests
- Volume tested up to 1,000,000 events
- Total runtime: ~4102 seconds
- Average throughput: ~244 records/second
- Observed processing latency: <2 seconds per micro-batch

## Visualization
A lightweight visualization layer was added to illustrate aggregated streaming results over time.  
Due to local simulation constraints (single-producer execution and compressed event timestamps), a high number of windows may be flagged as suspicious. In a real-world deployment with naturally distributed traffic, the same detection rules would operate on more balanced windows and produce more selective alerts.

## Notes
- This project is developed for **educational and portfolio purposes**.
- The implementation prioritizes clarity, correctness, and reproducibility over production hardening.
- The pipeline can be extended with advanced fraud detection models, monitoring dashboards, and cloud-based deployment.
